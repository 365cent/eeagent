# Dify 网页抓取工具替代采集客户端调研

- 日期:2026-10-30
- 核心问题:**能否用 dify 网页抓取工具返回的信息做分析, 从而不再需要 `client/` 的独立抓取客户端?**
- 调研素材:本次工作流的探测记录(probe)、链路与职责分析(surface)、替代方案分析(altAnalysis);原始 JSON/截图证据已从仓库移除,结论与正文引用仍保留(标注"报告人复核"处为撰写当时核对记录)。
- 密钥处理:aihub 应用密钥明文**不写入本报告**,仅引用其 `backend/.env` 变量名 `eea_aihub_crawl_api_key`。

---

## 1. 结论先行

**不能——dify 网页抓取工具这条路径已被实测证伪, 不能替代 `client/`。**

判定分三层:

1. **dify/aihub 抓取路径:❌ 不可用(已证伪)。** 调用链路本身稳定(REST 全链路 6+1 次实测打通),但对本平台的采集目标——微信公众号文章——**系统性拿不到正文**(两篇实测均仅返回 98 字符的标题+导航碎片),对 JS 渲染页和反爬站同样失败。探测结论 `usable=false`,理由与实测一致(素材 probe.usable / probe.limitations ⑥)。
2. **"client 从架构中完全移除":不可行, 也不值得追求。** client 承担四类服务端无对等方案的职责:登录态、企网无出网的部署约束、人机验证现场处置、JS 渲染完整性(surface.clientOnly,四条各有文件级证据)。
3. **但有条件地"免去人工逐篇采集"是可行的, 且门槛比原估低。** 调研中的补充实测发现:公众号正文本就在原始 HTML 的 `#js_content` 里, 用本机直连 `curl` + 后端现成的 `parse_html_snapshot` 即可拿到 2,813 / 4,969 字符的完整正文(素材 altAnalysis 一、#1-#2)——**正文提取能力恰好在我方手里, dify 失败是它自己的抽取层失效**。真正的出路不是任何外部抓取服务, 而是把现成抓取件挪到"具备出网的采集节点"上无人值守——`docs/platform-implementation-plan.md:706` 早已预留该形态(原文含"或具备出网的采集节点",报告人复核)。

> 一句话:**dify 路线死掉不影响大局; client 的可下线部分是"人", 不是"进程"。**

### 2.4 工具局限(素材 probe.limitations 汇总)

1. **正文完整性**:公众号系统性拿不到正文;换微信 UA 直接重试失败;JS 渲染页与反爬站同样失败——它是**无 JS 执行的静态抓取**,对微信类 SPA 化/反爬站点不可用。
2. **反爬失败有两种形态**:`status=failed` + error 字符串,或 `status=succeeded` 但 text 是"正在进行安全检测/不喜欢"类验证残留——若接入,后端须自行做正文有效性判断(长度阈值+关键词黑名单)。
3. **超时/频率**:blocking 单次 2.4~11.1s;平台文档明示长流程在 Cloudflare 层 100s 无返回会中断,建议 streaming;8 并发同打同一应用全部 200,未见平台限流,但密钥级 QPS 阈值无官方文档。
4. **返回格式**:伪 JSON、`total_tokens=0`、无状态码/最终 URL 字段;最长实测 1341 字符全量返回,无截断上限说明。
5. **应用性质**:`抓取测试-可删`(app `80d629b4`)是本次会话授权新建的一次性测试应用;任何正式接入应复制为 EEA 专用应用并换密钥,密钥只进 `backend/.env`。

### 3.2 client 承担、纯服务端 HTTP 抓取无对等方案的四类问题(素材 surface.clientOnly)

先记一条硬约束:**生产形态下服务端无公网出网**——`backend/TODO.md:130`"企网 API 不出网"、`client/TODO.md:207`"生产 API 无公网;仅 Capture Client 访问公网"、`docs/platform-implementation-plan.md:706`"企网部署时服务端无公网出网,网页与微信公众号的 HTTP 抓取在研究者本机(或具备出网的采集节点)执行"。三段原文报告人均已逐字核对。

1. **登录态**:公众号等需登录内容保存在本机浏览器 profile,首登扫码后续自动复用,且"客户端不接触账号密码"(`client/README.md:66,105`)。服务端 httpx 无法复刻。
2. **内网/网络拓扑**:出网能力在研究者本机而非服务器侧;服务端"直接拉 URL"在生产企网里连公网都到不了。
3. **反爬/人机验证**:`engine.go:263-265` 按 URL/文案特征识别微信 `wappoc_appmsgcaptcha` 与 Cloudflare 验证页,可见窗口最多等 180s 让人工完成验证(`client/README.md:72,107`)。服务端进程没有"让人在现场点一下"的交互面。
4. **渲染完整性**:连续两次采样文本长度不变且 ≥`min_text_chars` 才归档(`engine.go:306-347`);SingleFile `loadDeferredContent:true` 强制懒加载并内联 base64 图(`engine.go:423`)。后端依赖只有 bs4+html2text(`backend/pyproject.toml:11,14`;本会话 grep 确认无 playwright/selenium),且解析剥 img、archive 逐字节回放都以"自包含 HTML"这一 client 产物为前提。

另有一项 client 独有但非浏览器能力:已存 .html 离线归档通路(`archive.go:14,42-61`)。

**小结(素材原结论)**:client 不能下线。对"普通公开静态页",服务端抓取技术上可替代;但上述四类问题各自都无对等方案——"服务端拉 URL"只能作为并列的第三条入库路径,不是替换。

## 6. 遗留缺口与建议

### 6.1 各路径评估结论(素材 altAnalysis 二)

### 6.2 建议

1. **立即可做**:走 **C2 为主 + C1 兜底** 的出网采集节点方案。采集主力自动化后,client 从"人人的工作台工具"降级为"节点后台组件 + 特殊页面人工兜底通道"。后端**一行不用改**(复用 `/signals/capture` 契约);成本大头是组织流程(一台出网机器 + 防火墙/白名单申请),技术量级一天。
2. **保留 client 的不可替代面**(证据在案):人机验证现场处置(`engine.go:263-265` 的 180s 交互窗)、登录态内容(`client/README.md:66,105`)、JS 重渲染页;另 36kr 类反爬站在**任何**服务端路径下都失败(altAnalysis #4/#5)——"完全不依赖 client"的目标应放弃。
3. **若确要小补解析器**:在 `html_snapshot.py:204-229` 增加对微信 JS 变量 `createTime` 的正则回退,修复 #6 的 `published_at=None`,一处小改(本次未做)。
4. **任何后续接入必须落地的判别逻辑**:dify 型"成功但空壳"的失败形态要求正文有效性判断(长度阈值+关键词黑名单);失败时按 REQ-SIG-11 留 URL 行不标"已留存"(`client/TODO.md:209`)。
5. **密钥卫生**:若未来复用 aihub 测试应用,应复制为 EEA 专用应用并换密钥,明文只进 `backend/.env`(`eea_aihub_crawl_api_key`);测试应用 `抓取测试-可删` 保留期间注意其密钥已在会话中出现,正式接入前一律作废重发。
