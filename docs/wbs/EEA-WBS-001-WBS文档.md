## 一、项目与范围

### 1.1 项目目标

把电子电气架构（EEA）前瞻技术的推导过程搬到平台上，使一条技术判断从原始资料到战略结论的每一步都有记录、可追溯、可复核。

推导链路共七步：原始信号、需求点、车辆功能、技术落脚点、部署标准、战略研判。

### 1.2 本期交付范围

- 七个环节对应的平台功能页面
- 网页与微信公众号资料采集
- Word、PDF 文档上传与解析
- 平台内的对话助手
- 以 eFuse 案例为样本的全流程验收

### 1.3 本期不做

| 不做            | 说明            |
| ------------- | ------------- |
| 论文库、专利库抓取     | 下一期           |
| 统一身份认证        | 下一期，本期记录操作者姓名 |
| 手机端           | 本期只在电脑浏览器使用   |
| 雷达图、网络图等图形化分析 | 本期以列表和卡片为主    |
| 平台自动合并需求或排序   | 业务规则不允许，判断权在人 |

### 1.4 前置状态

第一周（技术选型、模型账号申请、数据表结构设计、同类平台调研）已完成。本计划覆盖剩余五周。

## 六、风险与变更

### 6.1 主要风险

| 风险            | 影响      | 应对                            |
| ------------- | ------- | ----------------------------- |
| 微信公众号抓取成功率不稳定 | 环节一验收受阻 | 抓取失败时允许手动粘贴正文并保留原链接，不影响其他功能   |
| 自动分类准确率不达标    | 环节二验收受阻 | 调整识别规则与示例；仍不达标则改为系统建议、人工确认必选  |
| 第四周全流程未贯通     | 影响整体交付  | 优先保证全流程贯通，对话助手和报告样式可延后        |
| 业务核对时间不足      | 验收无法完成  | 核对清单提前准备，电气工程师逐条打勾即可          |
| 关键知识集中在开发一人   | 后续难以维护  | 第四周起每周由电气工程师自行操作一次；第六周独立操作并录屏 |

### 6.2 进度压力

按当前范围估算，开发工作量约 230 人日，五周内单人可用约 25 人日，存在明显缺口。建议在评审时确定优先顺序：全流程贯通优先，对话助手与文档解析可推至下一期。

### 6.3 变更控制

计划确认后，新增需求按以下流程处理：

1. 提出变更，说明新增内容与必要性
2. 开发评估对工期和验收的影响
3. 电气工程师与评审共同判定：本期执行、推至下一期、不予执行
4. 本期执行的分配新编号并更新本文档
5. 其余记入 1.7.3 下一期需求清单

判定原则：影响 M3 全流程贯通的变更，一律推至下一期。
